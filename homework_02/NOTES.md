# Типи даних і пам'ять у C++ (ESP32)

## Аналіз коду

```cpp
uint8_t a = 200;
uint8_t b = 100;
uint8_t sum = a + b;
```

`uint8_t` — беззнаковий 8-бітний тип, діапазон значень `0..255`.

`a + b = 300`, але результат зберігається у `sum`, яка теж `uint8_t` і не може
вмістити 300. Відбувається **переповнення (overflow)**: для беззнакових типів
у C++ це поведінка добре визначена (не UB) — значення "загортається" за
модулем `2^8 = 256`:

```
300 mod 256 = 44
```

Отже `sum == 44`. На практиці компілятор ще під час обчислення `a + b`
підвищує обидва операнди до `int` (integer promotion), тому саме додавання
дає коректні 300, а втрата даних відбувається саме в момент присвоєння
результату назад у `uint8_t sum`.

**Висновок:** обирати тип потрібно з урахуванням максимального можливого
значення, яке в ньому реально зберігатиметься, інакше дані тихо
спотворюються без жодної помилки чи попередження під час виконання.

## Де "живуть" змінні програми

| Область пам'яті | Що там зберігається | Приклад із проєкту |
|---|---|---|
| **Flash (.text / .rodata)** | Скомпільований код програми, рядкові літерали, `const`-дані | тіла функцій `setup()`, `loop()`, текстові формати в `Serial.printf(...)` |
| **.data** | Глобальні / static змінні з ненульовим початковим значенням, копіюються у RAM під час старту | якби `lastSensorPrint = 1000` замість `0` |
| **.bss** | Глобальні / static змінні без явної ініціалізації (або з `= 0`), зануляються при старті, самого значення у flash не зберігається | `lastSensorPrint`, `lastHeapPrint` |
| **Heap** | Динамічна пам'ять, яка виділяється/звільняється під час виконання (`new`, `malloc`, внутрішні буфери Arduino/ESP-IDF, `String` тощо) | саме її обсяг показує `ESP.getFreeHeap()` |
| **Stack** | Локальні змінні функцій та параметри, автоматично звільняються при виході з функції | `SensorData data` у `readSensor()`, локальні `a`, `b`, `sum` у `overflowDemo()` |

Практичний момент для embedded: якщо `ESP.getFreeHeap()` стабільно
зменшується з часом (не коливається туди-сюди, а саме постійно падає) — це
ознака memory leak: десь відбувається `new`/`malloc` без відповідного
`delete`/`free`, або динамічно ростуть об'єкти на кшталт `String`. У цьому
проєкті всі змінні або локальні (стек, автоматично звільняються) або
глобальні статичні (`.bss`, виділені один раз назавжди), динамічного
виділення пам'яті немає — тому обсяг вільного heap має лишатися стабільним
протягом усього часу роботи.

### Спостереження з реального запуску

```
Free heap: 351076 bytes   (setup(), одразу після overflowDemo())
Free heap: 350812 bytes   (loop(), t=60s)
Free heap: 350812 bytes   (loop(), t=120s і далі — без змін)
```

Між першим і другим виміром heap падає рівно один раз на **264 байти**, а
потім лишається незмінним. Це не leak, а очікуваний одноразовий ефект:
`overflowDemo()` у `setup()` викликає `Serial.printf` лише з `%u`
(цілі числа), а перший виклик `printSensorData()` у `loop()` вперше
використовує `%.1f` (float). У ESP32 Arduino (newlib) буфер для
double-to-string конвертації, потрібний для форматування float у
`printf`/`vsnprintf`, не виділяється заздалегідь, а створюється при першому
виклику з `%f`-специфікатором (частина reentrant-структури newlib) і
лишається виділеним до кінця роботи програми. Тому heap "просідає" рівно
один раз на фіксовану невелику величину і далі не змінюється — це
відрізняє його від справжнього leak, де падіння продовжувалось би з кожним
новим виміром.
